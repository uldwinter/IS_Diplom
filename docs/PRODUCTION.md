# Публикация и перенос данных

## Перед выпуском

1. Сохраните копию существующей PostgreSQL и локальные JSON-копии со всех устройств, на которых велись реальные записи. Прежняя версия не синхронизировала эти устройства. Автоматически восстановить недоступные браузерные записи сервер не может.
2. Создайте изолированную тестовую БД или ветку существующей базы. Preview использует только её.
3. Установите зависимости, выполните `npm run check`, затем серверную миграцию на тестовой БД. Исходные серверные таблицы сохраняются.
4. Проверьте: регистрация → решение куратора → вход ученика → документ → достижение → модерация → рейтинг/отчёт в другом сеансе. Скачайте и восстановите резервную копию на тестовой БД.
5. Перед production сохраните отдельную копию БД; выполните ту же миграцию и проверьте состав записей. Переключайте приложение после готовности схемы и администратора. Старая версия не должна записывать в прежние таблицы после перехода.

## Vercel

Проект: `work_diplom`, команда `uldwinters-projects`. Frontend — Vite; `/api/v1/*` направляется в `api/index.mjs` с Express. Нужны серверные переменные:

- `DATABASE_URL` — pooled PostgreSQL с TLS; не задавать префикс VITE.
- `APP_ORIGIN=https://workdiplom.vercel.app` — точный origin рабочей публикации.
- `NODE_ENV=production`, `TRUST_PROXY=1`.

Для preview задайте отдельный `PREVIEW_DATABASE_URL`; origin определяется собственным `VERCEL_URL`. Рабочая база и preview не должны делить тестовые изменения. `VITE_API_URL` оставьте пустым для same-origin cookie.

`vercel.json` запускает установку зависимостей сервера, его тесты и клиентскую сборку с проверками. Схему не меняют ни сборка, ни каждый HTTP-запрос. Миграция запускается отдельно из `server` с direct connection string (без pooler) перед выпуском. Первая учётная запись создаётся `npm run bootstrap`; параметры берутся из окружения. Не публикуйте bootstrap-пароли в логах или клиентской сборке.

Размер файлов согласован с ограничениями HTTP-платформы. Для больших резервных копий используйте серверную CLI-команду из `server/README.md`, которая обращается к PostgreSQL напрямую. При необходимости файлов больше лимита понадобится прямое объектное хранилище либо отдельный API-хост; увеличение поля формы не обходит лимит Vercel.

## Docker / VPS

Используйте `docker compose` с `DB_PASSWORD` в корневом `.env`. Сервис web проксирует API через nginx — браузер не обращается к localhost пользователя. PostgreSQL не публикуется наружу; том pgdata сохраняется. Миграция — отдельная команда `docker compose run --rm api npm run migrate`, затем `docker compose run --rm -e ADMIN_LOGIN -e ADMIN_EMAIL -e ADMIN_PASSWORD api npm run bootstrap` и `docker compose up -d`. Seed автоматически не запускается.

Снаружи нужен HTTPS reverse proxy. Укажите внешний `APP_ORIGIN` и `TRUST_PROXY=1` только за доверенным reverse proxy. Для Docker локально cookie может быть без Secure; для публичной рабочей среды необходим NODE_ENV=production и HTTPS.

## Восстановление и откат

Проверяйте восстановление в изолированной базе. Серверная копия включает бинарные документы. После восстановления все прежние сеансы завершаются, а факт восстановления сохраняется в аудите. Сначала сохраните текущее состояние: восстановление заменяет доменные записи. При откате к старому клиенту нельзя ожидать, что он прочитает новую общую базу — старый клиент использует localStorage. Безопасный откат новой версии должен сохранять серверный источник данных.

Не удаляйте сохранённые legacy-таблицы до проверки количества пользователей, регистраций, достижений и согласованности истории. Старые записи без настоящих вложений не должны выдаваться за проверенные файлы; новые подтверждения требуют реальных документов.
